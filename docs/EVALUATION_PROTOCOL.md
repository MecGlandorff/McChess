# Evaluation Protocol

## Goals

Evaluation should answer:

1. Does the model beat simple baselines?
2. Does MCTS improve the model?
3. Which architecture performs best under fixed compute?
4. Which model gives the best strength per second?
5. Which components matter in ablations?

## Baselines

Required:

- random legal-move bot
- material-count bot
- minimax depth 1
- minimax depth 2
- policy-only neural bot
- policy/value + MCTS bot

## Match Protocol

Default arena:

- alternate colors
- fixed seed
- fixed number of games
- max ply limit
- legal moves generated by python-chess
- adjudicate draw at max ply if no terminal result
- record illegal move count
- record checkpoint and config identifiers
- record wall-clock runtime when practical

Recommended minimum:

- fast smoke: 20 games
- development eval: 100 games
- reportable eval: 400+ games

## Opening Positions

When comparing two agents or checkpoints, use the same opening-position protocol for both sides.

Acceptable protocols:

- standard initial position only
- fixed list of opening FENs
- sampled opening positions saved to a manifest

For reportable comparisons, record the exact opening source and ensure both agents play both colors from the same positions when practical.

## Budget Types

Do not mix budget types in a comparison without saying so.

Common budget types:

- policy-only, no search
- fixed MCTS simulations per move
- fixed wall-clock time per move
- fixed total game clock

Report node budgets and wall-clock speed separately. A model that wins more games but runs much slower should not be presented as strictly better without speed context.

## MCTS Budgets

Evaluate at:

- policy only
- MCTS-25
- MCTS-50
- MCTS-100
- MCTS-400

When possible, also report wall-clock speed.

## Metrics

Report:

- wins
- draws
- losses
- score percentage
- average game length
- illegal move count, should be zero
- nodes/sec for MCTS
- inference positions/sec
- policy top-k accuracy
- value MSE
- value calibration
- confidence interval or uncertainty estimate for reportable win rates when practical

For score percentage, use:

```text
score = (wins + 0.5 * draws) / games
```

## Supervised Checkpoint Evaluation

Use `scripts/eval_top1.py` for held-out supervised policy/value evaluation. It
reads a YAML config, evaluates a checkpoint against a JSONL shard, and writes a
JSON result artifact.

The JSONL shard is required for legal-masked policy metrics because the
evaluator reconstructs each FEN and uses `python-chess` plus
`legal_policy_mask(board)`. Tensor caches do not store FENs and are not the
source of truth for legal top-k evaluation.

The result JSON records:

- checkpoint path, checkpoint epoch, and checkpoint metadata
- dataset path, manifest path, split, seed, device, batch size, and sample count
- policy cross-entropy and legal-masked policy cross-entropy
- raw top-k accuracy and legal-masked top-k accuracy
- raw argmax legal fraction
- value MSE, RMSE, MAE, zero/mean baselines, and relative MSE improvement
- prediction distribution, decisive sign accuracy, calibration buckets, and ply
  buckets

Use validation data for tuning choices such as checkpoint selection,
normalization variants, loss weights, or reranking. Use test data for the final
reported number under a fixed config.

## Reportable Result Gate

A result is reportable only if it includes:

- number of games
- wins/draws/losses
- score percentage
- seed
- color alternation policy
- max ply and draw adjudication rule
- opening-position protocol
- model checkpoint or bot version
- opponent checkpoint or bot version
- MCTS budget or policy-only declaration
- illegal move count
- evaluation config path or saved config copy

## Fairness

When comparing architectures:

- same dataset
- same train/val/test split
- same number of training steps if possible
- same MCTS node budget
- same opening positions
- same random seeds
- report parameter count and speed

For two-agent comparisons, prefer paired comparisons:

- same openings
- swapped colors
- same search budgets
- same max ply and adjudication rules

If a comparison is not paired, state that limitation.

## Claims

Do not claim Lichess Elo unless actually measured on Lichess or through a careful rating protocol.

Prefer:

```text
In our local arena, model A scored X% against baseline B under protocol C.
```

Avoid:

```text
Model A is 1800 Elo.
Model A is objectively stronger.
Model A is close to leading chess engines.
```

unless the exact claim is supported by a documented protocol.

## Result JSON Fields

Arena result files should include:

```json
{
  "run_id": "",
  "status": "completed",
  "seed": 0,
  "num_games": 0,
  "wins": 0,
  "draws": 0,
  "losses": 0,
  "score": 0.0,
  "illegal_moves": 0,
  "max_ply": 0,
  "draw_rule": "",
  "opening_protocol": "",
  "agent": "",
  "opponent": "",
  "agent_checkpoint": null,
  "opponent_checkpoint": null,
  "mcts_budget": null,
  "eval_config": "",
  "started_at": "",
  "completed_at": ""
}
```
